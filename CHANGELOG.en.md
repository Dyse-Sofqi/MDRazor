### Changelog

**2.7.1** (2026-10-09) — Fixes the "Clean Orphan Images" toggle in the Left Ribbon tab: turning it off now unregisters the button and its action immediately (the trash button used to stay in the left ribbon, still ran the cleanup when clicked, and stayed listed under Hidden Commands); fixes custom commands whose bound command id no longer exists doing nothing at all with no feedback (a notice now names the missing command); fixes a new line created with Enter not being indented while "First-line indent" is on (the caret stayed un-indented until the first character was typed)

**Fixed**

- **With "First-line indent" on, a line created with Enter was not indented (the caret did not line up with the indent)** — The indent is driven by a CM6 line decoration, and the paragraph-first-line decision excluded **blank** lines (they classify as `blank`, not `text`): the line created by Enter is empty, so it got no decoration and the caret sat at the un-indented position; as soon as a character was typed the line became a body line, the decoration appeared, and the caret and text jumped to the indent together. Blank lines now take part in the paragraph-first-line decision (treated as "would this line be a paragraph start if it were a body line", i.e. the same rule as body lines), and blank lines get their own decoration class that shifts the content box right by one indent width using a **transparent inline-start border** — `text-indent` only shifts the inline content of the first line box, and an empty line has none, so the browser still drew the caret at the un-indented position (measured: the `<br>` of an empty line was already at 38px while the content box left edge was still 6px). The transparent border was chosen over margin / padding on measured evidence (see DEBUGLOG): margin also pushes the line box, which clips a corner off whole-line backgrounds such as the active-line highlight; padding **replaces** rather than adds to the base padding and corrupts the text-area base CM6 reads from the first `.cm-line`'s `paddingLeft`. Adds mechanism pages `scripts/fixtures/first-line-indent-empty-line-shift.html` and `first-line-indent-caret.html`; `npm run verify:indent` gains blank-line cases (an Enter-created empty line must be indented in non-strict line breaks, not in strict mode, and blank lines inside fenced code blocks must not be indented).
- **A custom command whose bound command id no longer exists did nothing at all, with no feedback** — Custom commands on the ribbon / status bar / context menu store a command id and run it via `app.commands.executeCommandById(id)`. Obsidian's `findCommand` is a plain id lookup and `executeCommandById` **returns `false` without throwing** for a command that does not exist (verified by unpacking app.js), while the old implementation only caught throws — so the `false` was swallowed silently: no notice, no log. After a plugin is renamed or uninstalled its command ids stop resolving and the button becomes "clicking does nothing", with no way for the user to tell why (real case in this vault: style-tuner 1.1.x renamed the command id `show-style-tuner-leaf` to `show-view`). It now checks existence with `findCommand` first: missing → a notice naming the id ("Command not found (renamed or removed plugin?): <id>"); present but returning `false` (the host also returns `false` when a callback throws) → "Failed to execute command". `npm run verify:ribbon` gains 7 assertions covering all three cases (missing command / working command / throwing callback).
- **Turning off "Clean Orphan Images" did not actually unregister the left-ribbon trash button** — The button is registered through `Plugin.addRibbonIcon()`, which, besides returning an element, registers an entry inside `workspace.leftRibbon` under the action id `${plugin id}:${title}` (verified by unpacking Obsidian's app.js). The old removal only detached the element from the DOM, leaving the entry in `leftRibbon.items` with its `buttonEl` intact — and on every `refresh()` the plugin's own ribbon manager re-appends **every** item that still has a `buttonEl` back into the container (that is how it syncs drag-reordering and hide/show). The button therefore came straight back the moment the toggle was switched off, kept running the cleanup on click, and stayed listed under Hidden Commands as a renderable entry. Removal now calls `leftRibbon.removeRibbonAction(id)` to unregister properly (clearing the entry's `buttonEl` and `callback` while keeping the entry itself, so re-enabling reuses it by id instead of stacking duplicates), the ribbon manager skips entries with no `buttonEl`, and the settings panel repaints the list right after the toggle so the entry disappears at once. Adds an offline regression, `npm run verify:ribbon` (including a counter-example guard: detaching the element without unregistering makes the button reappear, which keeps the regression sensitive to the original bug).

**2.7.0** (2026-10-08) — Callout enhancement: collapsible callouts (`[!type]+` / `[!type]-`) now fold/expand when their title area is clicked (natively only the fold arrow inside the title row responds; the "Edit this block" button is never covered, and dragging to select title text does not trigger a fold)

**Added**

- **Callout enhancement: click a collapsible callout's title area to fold/expand** — In Live Preview, Obsidian's native fold switch only recognises the fold arrow (`.callout-fold`) inside the title row: clicking the rest of the title (icon / title text) does nothing, and since the Callout enhancement already intercepts title-area clicks wholesale to keep the callout rendered, the title area was a dead zone. Clicking a collapsible callout's title area now toggles the fold. The implementation **replays one synthetic click on the fold arrow** and leaves the state change entirely to Obsidian's own handler (no assumption about which class / aria attribute holds the fold state — the same code path as a real arrow click), with the real click intercepted first so the callout stays rendered. Four boundaries are guaranteed: the "Edit this block" buttons (native and touch) are branched off before this path and are never covered; a click on the fold arrow itself keeps its native pass-through and never stacks a second toggle; dragging to select title text (mousedown-to-click displacement over 5px) does not count as a click — no fold, and the title stays drag-selectable; and while an in-place edit session is open the title area does not toggle (the toggle would be invisible, and cancelling the edit does not rebuild the widget, which would leave a stray collapsed state). Non-collapsible callouts keep their previous "keep rendering only" behaviour on title clicks, and nested callouts toggle only the layer that was clicked. No pointer cursor is added — Obsidian's default appearance is deliberately left untouched, with no extra affordance for the fold gesture. A new offline regression `npm run verify:callout-fold` covers 34 assertions (branch order, the three gates, the edit-session guard, nesting, drag and blank-area non-triggers).

**2.6.9** (2026-10-07) — Fixes reversed typing / characters landing outside the marks in Live Preview when the caret sits under a hidden range in an empty inline code span (pressing `` ` `` at the start of a line auto-pairs into an empty pair with the caret in the middle, where the DOM has no text to host the caret and every keystroke lands after the marks); the marks covering or pinching the caret now reveal briefly (matching native Live Preview) and hide again as soon as the first character is typed

**Fixed**

- **Live Preview: typing inside an empty inline code span came out reversed, outside the backticks (reported: typing `123456` rendered `654321`)** — With formatting marks always hidden, pressing `` ` `` at the start of a line makes Obsidian's auto-pairing (`autoPairMarkdown`) insert a pair and put the caret **between** the two backticks, while the parser builds the whole backtick run as a single node and the plugin hides that run as one range: the caret ends up **inside a hidden range**, where the DOM has no text to host it. Chromium normalises the DOM caret to just after the placeholder while CM6's state caret stays put, so every keystroke is inserted at that same position — characters land outside the marks and come out reversed (` ``321 `), and the symbol-boundary tooltip, reading the state caret, keeps showing `` `|` ``. The same degenerate position also occurs when the caret is pinched between two adjacent hidden ranges (empty spans split into two marks). The plugin now reveals the ranges that **cover or pinch** the caret (matching native Live Preview: asar evidence shows it emits no hide decoration when the cursor intersects a mark, plus a dedicated plugin that snaps the cursor out of hidden ranges), so the caret falls back onto real text and the insertion point becomes determinate; the marks hide again as soon as the first character is inserted. The rule lives in the pure module `caret-reveal.ts` (collapsed caret only; every other state is untouched), with a new offline regression, `npm run verify:caret` (20 assertions).

**Improvements**

- **Hidden Styling: caret visibility** — when the collapsed caret sits inside a hidden range or is pinched between two adjacent hidden ranges (degenerate positions such as an empty inline code span or an empty bold pair, where no text exists on either side of the caret), the marks at the caret reveal so the insertion point always lands on real text; they hide again as soon as the first character is typed — imperceptible in normal editing and visually consistent with native Live Preview, which reveals marks whenever the cursor intersects them.

**2.6.8** (2026-10-04)

**Added**

- **Callout touch edit button (new setting, on by default)** — On devices without hover capability (iPad, phones, …), an edit button (pencil icon) now stays visible at the top-right corner of every callout. The native "Edit this block" button shows on hover only (app.css: its container defaults to `opacity: 0` and only hover restores it), so on touch devices it is permanently invisible and users have to tap the corner blindly; worse, the transparency sits on the parent container, so user CSS with `opacity: 1 !important` on the button itself cannot fix it. The plugin button is injected incrementally by a MutationObserver and displayed only inside `@media (hover: none) and (pointer: coarse)` — desktop hover environments are pixel-identical and keep using the native button.

**Fixed**

- **List integration: extra spaces after a list marker (`- ` / `1. `) were treated as part of the list formatting** — HyperMD's list-marker node swallows every whitespace character that follows the marker, and the atomic range took the node as-is, so the extra spaces fell inside the "cursor can't rest here, deletion expands as a whole" protected span: ArrowLeft could not move the cursor back across the spaces (it got stuck right after all of them) and Backspace wiped the marker together with every space in one stroke. The atomic range is now shrunk to "marker + exactly one space" (matching the native task-line format boundary): extra spaces become ordinary text, ArrowLeft moves across them one by one, and Backspace deletes one space at a time — only at the marker's right edge (`- |`) does it remove the whole unit or trigger "Backspace promotes level". The checkbox merge was tightened accordingly: `-   [ ]`, which the native task-line rule does not render as a checkbox, no longer swallows its inner spaces into the atomic range. Adds an offline regression: `npm run verify:list`.
- **Callout editor opened silently with an empty body when the body line started with a zero-width character copied from the web** — JS `\s` does not include ZWSP/ZWNJ/ZWJ/word joiner/soft hyphen (U+200B–200D, U+2060, U+00AD), so a body line carrying one after the leading whitespace no longer matched `^\s*>`, was evicted from the quote-line span, and the body collection ended early; Obsidian's own rendering was unaffected, so the block still rendered with its body — two inconsistent views of the same source. Line-level detection and prefix stripping now tolerate `\p{Cf}` format characters uniformly (extracted into the pure module `callout-parse.ts`), with all semantic boundaries preserved (at most one character stripped after `>`, zero-width characters inside the body kept as-is, the header prefix written back verbatim). Adds an offline regression: `npm run verify:callout` (28 assertions).
- **The callout editor had no way to cancel** — the Done button, tapping outside the panel, and Esc all committed; a mistaken edit could not be abandoned without writing back. The panel now has a Cancel button, and Esc discards as well (closing without writing back); Done and tapping outside keep committing.

**2.6.7** (2026-10-01)

- **New "First-line indent" setting (off by default): indents the first line of body paragraphs, excluding every non-body block** — a toggle plus a width slider (1–2 CJK characters, `1em` = one CJK character) in the General section. The paragraph decision runs through a purpose-built line classifier (a pure function, no dependency on the host's syntax tree) and excludes headings, tables, unordered/ordered lists, blockquotes and callouts, fenced code, math blocks, comments, HTML blocks, frontmatter, footnote and link reference definitions, standalone block IDs, and paragraphs holding nothing but an image. **Applies to Live Preview and Reading view only; source mode is deliberately excluded** (indenting there would push the source itself right, looking like stray typed spaces). In the editor the indent is driven by CM6 line decorations, in the reading view by the stylesheet; both share one width variable. The setting's description spells out its scope and exclusions.
- **Fix: the paragraph boundary of first-line indent ignored Obsidian's "Strict line breaks" setting** — the boundary used to follow CommonMark semantics ("consecutive text lines are one paragraph, only the first line is a first line"), but Obsidian's **default is non-strict** (a single newline is a hard break when rendered). Users writing paragraphs with single Enters therefore had "one line = one paragraph", and every body line after the first missed its indent. The setting now reads `app.vault.getConfig('strictLineBreaks')` and follows it: in non-strict mode (the default) every body line is a paragraph first line and gets indented, while strict mode keeps the previous behaviour (continuation lines of the same paragraph are not indented). Changing the setting repaints immediately (subscribing to `config-changed` and filtering on that key), and the flag is part of the paragraph-cache key.
- **Fix: first-line indent leaked into third-party views such as Glimpse's teleprompter** — two scopes were too wide. On the reading-view side the selector was `.markdown-preview-view p`, but `markdown-preview-view` / `markdown-rendered` are generic hooks third-party views attach to their own containers to borrow theme typography (the teleprompter's content container is `glimpse-tp-content markdown-rendered markdown-preview-view`), so its paragraphs got indented too. On the editor side the line decorations are registered with `registerEditorExtension`, which attaches to **every** CM6 editor in the workspace (including editors built by third-party views). The reading-view rules are now prefixed with `.markdown-reading-view` (exclusions included) and the editor side requires `view.dom.closest('.markdown-source-view')` in `build()`. **Both sides had to be narrowed** — the editor side is a JS decoration, so fixing the stylesheet alone would not have been enough.
- **Fix: in the reading view, lines after the first were indented by roughly 0.3–0.4 of a character too much** — the spacer used to be inserted between the `<br>` and the text node that follows it, but markdown-it renders a soft break as `'<br>\n'` (the `<br>` is followed by a newline that the HTML parser folds into the start of the next text node, giving DOM like `"\nsecond line"`). That leading whitespace therefore no longer sat at the start of the line, so the "drop leading whitespace" rule did not apply and it collapsed to **a single space**, pushing the line right by one space (measured: continuation lines at 44.73px against a 40px first line — 4.73px at a 16px font size is 0.3em, exactly one space). The spacer is now inserted **after** the leading whitespace (`splitText`, leaving the whitespace behind the `<br>`); both line starts measure 40px afterwards.
- **Fix: the reading view had no per-line indent (lines after a single Enter were not indented)** — in the reading view a single Enter is just a `<br>` inside a `<p>`, and `text-indent` only applies to the first line of a block box, so text after a `<br>` cannot be indented (all four pure-CSS approaches were measured and none works — see below). Each `<br>` in a body paragraph now gets an **empty inline-block spacer** after it that pushes the line right: an empty node never enters the text content (copying a selection is unaffected), `height: 0` keeps the paragraph's height pixel-identical (measured 76.78 = 76.78), the width comes from a CSS variable (changing it needs no re-insertion), and undoing is just removing the classed nodes. Insertion is driven by a `MutationObserver` (`childList+subtree`, coalesced with rAF) whose `apply()` is idempotent (it only touches the DOM when something must be added or removed, so it cannot feed itself), and containers are de-duplicated with a `WeakSet`. Spacers are only inserted when the feature is on **and** line breaks are non-strict (under strict breaks a `<br>` can only come from an explicit hard break, which is still the same paragraph and should not be indented).
- **Fix: "settings only take effect after restarting Obsidian"** — the chain was first proven sound (a static audit of the consumption points of all 64 settings keys, a mechanical audit of all 38 `Setting` blocks in the panel with no omissions, a source-level confirmation that an empty transaction really does reach `ViewPlugin.update()`, and a real-CM6 end-to-end test where toggling the setting off/on/off produced 0/3/0 line decorations), and then four genuine gaps were closed: ① **the propagation chain could be silently cut by a single exception** — `syncConfig()` → `repaintAllEditors()` → `dirFileCountRefresher.forceRefresh()` ran back to back in `saveSettings()`, so any throw aborted the rest with no log at all, which looks exactly like "the setting saved but the plugin did nothing until a restart"; each step is now wrapped in try/catch with `console.error`. ② **body runtime state was only applied to `activeDocument`** — editors in popout and floating windows never received the body toggle classes or CSS variables; the new `window-scope.ts` provides `forEachDocument()` which walks the main window plus every leaf's document (de-duplicated by document, identified via `node.ownerDocument ?? node`, because a popout's document comes from another realm where `instanceof Document` fails), and all four body-class modules now apply window-wide. ③ **repainting used `instanceof MarkdownView`** — popout views live in another realm, so the check was false and those editors were never repainted; it now uses a duck test with a try/catch around each editor. ④ **the symbol-boundary hint popup stayed on screen after the setting was turned off** — its `update()` only refreshed on selection/document/geometry changes, while changing a setting dispatches an empty transaction, so a visible popup lingered until the next cursor move; a "toggle flipped" check was added that also clears the position cache. A new self-healing `applyRuntimeClasses()` (idempotent, per-item exception isolation) is called from `saveSettings()`, `workspace.on('layout-change')` (to attach runtime state when a new popout opens) and the settings tab's `display()` (so opening the panel heals it).
- **Performance and interaction of first-line indent** — the paragraph decision is cached per document object (line classification is an O(lines) whole-document scan, recomputed only when the document object actually changes, so pure cursor movement and scrolling reuse the previous result), and decorations are only built for first lines inside the visible ranges. `text-indent` does not break CM6's cursor positioning (`posAtCoords` goes through layout-aware interfaces, so click targets and selection rectangles follow automatically).
- **Why a line classifier instead of the host syntax tree** — Obsidian's CM6 markdown tree has **no block-level nodes at all** (verified by unpacking `obsidian-1.13.7.asar`): it is a CM6 port of HyperMD's streaming mode whose node names are simply the token string with spaces turned into underscores (`formatting_formatting-strong`, `HyperMD-header_HyperMD-header-1`), and its `parseLine` only emits a node for lines carrying a line-class token — plain text lines produce nothing. There is no `Paragraph` and no `BulletList` to find, so block structure has to be decided by this module. Its expected values are cross-checked against `@codemirror/lang-markdown` (the CommonMark+GFM reference implementation) on a shared fixture, with four deliberate deviations documented in the script.

**2.6.6** (2026-09-28)

- **Checkbox Integration enhancement: "← selects the checkbox character" — rewrite the checkbox status with the keyboard alone, without leaving Live Preview** — Checkbox Integration parks the cursor at the task item's content start (`- [ ] |`), where ← used to move into the marker range and get pushed straight back by the cursor correction — a dead key — so the status character between the brackets was uneditable by keyboard (user feedback: changing the completion state required clicking the checkbox widget or walking the Backspace chain). ← at that boundary now **selects the status character** instead: while selected, the selection touches the marker range, so Obsidian's cursor-aware decorations tear the checkbox widget down to raw text (`- [ ]` shown as characters with the status character highlighted; the list bullet is unaffected — the selection does not touch the list-marker range); typing any character replaces the selection, the resulting cursor lands back inside the atomic range and the existing correction resets it to the right boundary while the checkbox re-renders (`- [typed] |`); pressing ← / → again with the selection active natively collapses it and the correction lands on the right boundary — "cancel selection, back to the right edge". Backspace with the selection active deletes natively (leaving `- []`, which turns back into a task as soon as a character is typed). The only new interception is ← plus a selection dispatch; everything else reuses existing machinery (selections are skipped by the cursor correction, and the widget teardown/restore and cursor reset are native behaviour plus the existing correction chain). Works in both Live Preview and source mode (no mode gating, same as the Backspace interception); depends on Checkbox Integration only (the checkbox atomic range exists even with List Integration off); no new setting.
- **Fix: Enter soft break's checkbox inheritance only accepted `[ ]/[x]/[X]` — task items with any other single-character mark degraded to plain list items on continuation** — when a blank continuation line was upgraded into a list item (pressing Enter twice to create the next item), the inheritance test `/^\s*\[[ xX]\]/` matched the checkbox after the list marker on the item's first line: Minimal theme's `[-]` (incomplete), Tasks' `[/]` and `[>]`, and user marks like `[z]` (as in issue #16) all missed it, so the created item lost its checkbox. The test now matches Obsidian's native task-line rule — **any single character** between brackets counts (the new test `/^\s*\[.\] /` mirrors the core `bO` task-line regex `\[(.)\] ` extracted from the asar; the native checkbox widget's checked state is likewise "status character ≠ space"), and it adopts the native "a space must follow `]`" rule as well: space-less spellings like `[x]task` never rendered a checkbox natively and Enter never continued them as tasks, so inheritance does not fire either, and `[[` (wikilink start) cannot false-positive. New items still start unchecked as `[ ] ` (matching Obsidian's native Enter-on-task behaviour; custom marks are filled back in afterwards by plugins like Task Collector).

**2.6.5** (2026-09-27)

- **Callout enhancement (new setting, on by default): single-click keeps the rendered callout, "edit this block" opens an in-place editor, multi-line paste auto-fills the `>` prefixes** — ① in Live Preview, clicking a callout no longer falls back to the `>` quote source: a rendered callout is a CM6 block-level replace widget, and Obsidian's click handler dispatches a selection covering the widget's whole source range — as soon as any selection overlaps that range (touching the boundary counts), the widget is withdrawn. That dispatch is now blocked at the capture phase so the callout stays rendered, and only event propagation is stopped, not the browser default — text inside the rendered callout can still be selected by dragging, and links, fold arrows and embedded blocks keep working. ② the "edit this block" button in the top-right corner opens an in-place editor that keeps the official rendered look (border, background, radius, colours, icon and theme variables untouched): the title input sits inside the official title row (pixel-identical font, colour and line-height), the body textarea replicates the official `.callout-content` padding and background, and three more fields cover type / metadata / fold; on commit a single transaction rebuilds "title + body" back into `> [!type|metadata]fold title`, nothing is written to the document while editing (the widget is never rebuilt mid-typing), and if the source range was changed externally the write-back is abandoned with a notice instead of overwriting. ③ pasting multi-line text into the body normalises it (CRLF/CR → LF, existing `>` prefixes are stripped to avoid `> >` double quotes, trailing whitespace removed) and every line gets a uniform `>` prefix on commit (blank lines get a bare `>`); a conservative CM6 paste fallback expands line-initial multi-line pastes with the `>` prefix, everything else keeps native pasting.
- **Inline code enhancement (new setting, on by default): double-click inline code to copy it** — double-clicking inline code (`` `code` ``) in the editor copies its full content (without the backticks) to the clipboard with a "Copied" notice: no preventDefault and no transactions, so native double-click word selection and friends keep working untouched and the copy happens on top of them; the code range is resolved from the CM6 syntax tree (a `formatting-code` + `inline-code` mark pair — the production-proven approach used by format-hider) rather than any specific DOM structure, falling back to a DOM-boundary estimate when the tree has not caught up, and any failure hands control back to the native behaviour (correctness first); Shift/Ctrl/Alt/Meta double-clicks (word-selection extension), single clicks and drag selections are unaffected; fenced code blocks carry no inline-code class and are excluded naturally; applies in the editor (Live Preview/source mode) only.
- **The type/metadata suggestion dropdown no longer overflows the screen and follows the input when the editor scrolls** — the first version used a native `input[list]` + `datalist` popup, which is drawn by the browser and has two hard limitations (both user-reported): ① its size and styling cannot be controlled — the type candidates are the union of "30+ built-in entries ∪ values scanned from themes/snippets ∪ values used in the document" (70 measured), and the popup simply ran past the screen; ② the popup is positioned in screen space and managed by the browser, so when the editor scrolled it stayed behind while the input scrolled away with the content. It is now a custom dropdown: absolutely positioned inside the field, sharing the editor content's scroll context, so **following the scroll is guaranteed by construction** (no scroll listeners or repositioning); it is height-capped (`min(16rem, 40vh)`) and scrolls internally, with `overscroll-behavior: contain` preventing the scroll from chaining into the editor at the end of the list; suggestions filter case-insensitively as you type; ↑/↓ move through candidates (wrapping), Enter selects, Esc first closes the dropdown (pressing again commits and closes the panel); on open, the remaining space between the input and the editor scroller's bottom/top edges decides whether it opens downward or flips upward, so a panel near the bottom of the viewport no longer gets clipped. Three companion fixes — after a retest showed the dropdown still "confined inside the callout's display area", the core app.css was extracted from the asar and revealed the real culprit: ① **overflow** clipping is lifted — the core and this vault's Callout.css snippet both set `overflow: hidden` on `.callout`, and the core's `.cm-embed-block:hover` does too; the editing state now forces `overflow: visible`; ② **`contain: paint`** clipping is lifted — the core puts `.cm-content > [contenteditable=false] { contain: paint !important }` on block widgets, clipping all descendants to the widget's box in a way `overflow` cannot undo; the editing state adds `contain: none !important` on the widget, plus `isolation: isolate` (the render-state paint isolation also neutralises the callout's `mix-blend-mode` — this vault's theme passes `darken` — so without the replacement the editing-state colours would shift) and `z-index: 1` (so the dropdown that now extends past the widget paints above sibling embed blocks that follow it); ③ `paste` / `drop` events are now in the panel's propagation-blocking list — previously pasting into the type/metadata inputs bubbled all the way into CM6, where the paste-fallback extension would write the content into the document and rebuild the widget if the CM selection happened to sit at the start of a callout source line — destroying the editing panel and its uncommitted content on the spot (latent bug, fixed in passing).

- **The body textarea of the callout editor panel now grows with its content** — the textarea in the "edit this block" panel only had `min-height: 5em` and no grow-to-fit logic: as soon as the content exceeded the initial height a scrollbar appeared (user-reported), and long text had to be read inside a small fixed window. The height is now fitted by JS: after every `input` the height is set to `auto` and then to the measured `scrollHeight` (without the reset the height would never shrink when content is deleted); the first measurement runs **after** the widget width-limit class is applied (measuring against the rendered 200px-wide widget would overestimate the height); width changes such as window resizes alter the line wrapping and are re-fitted through a ResizeObserver, otherwise the scrollbar reappears whenever wrapping increases; pasting is a programmatic value assignment (no `input` event), so it re-fits explicitly. The `resize: vertical` handle is removed — a manually dragged height is overridden by the next keystroke, so the two contradict each other. Dynamic styling goes through `setCssProps` per the review rules (direct `element.style.height` assignment trips `obsidianmd/no-static-styles-assignment`).

- **Code blocks no longer take part in the mouse/wheel line highlight** — the highlight used to apply to every line in the editor, code-block lines included: moving the mouse over a code block raised a translucent accent wash (plus a 22px bleed shadow) across the whole line, covering the block's own background and syntax colours and blurring its left and right edges. Lines of a fenced code block (`.HyperMD-codeblock`, including the two fence markers) and the block-level widget an inactive code block is replaced with in Live Preview (`.cm-preview-code-block`) are now excluded, so code blocks keep the theme's own colours. A related glitch is fixed along the way: with the pointer resting on an inactive code block, scrolling used to highlight "the line at the centre of the editor" — the code-block widget belongs to no line, so it was mistaken for "the pointer is not over a line" and triggered the centre fallback; that no longer happens.
- **Code blocks keep their native cursor** — the same feature's arrow-cursor fallback (which swaps the I-beam for an arrow while hovering a line) used to cover code blocks as well, leaving no text cursor there. The whole code-block subtree now restores the native cursor: source-mode lines go back to the I-beam, and the block-level widget of an inactive code block returns to its own cursor. This needs separate handling — a `*`-wildcard "harden the whole editor while moving" rule also swallows code blocks, so adding `:not()` to the hover rule alone is not enough.

- **Hot-reloading this plugin no longer needlessly reloads the plugins under lazy-load management (destroying their views)** — `start()` runs on every `onload`, and the old implementation flipped any managed plugin that was merely *loaded*, three seconds later, through `flipToLazy()` (`disablePluginAndSave` + `enablePlugin`). At startup that path is correct (it converts a plugin Obsidian loaded naturally into lazy-load steady state: persistently disabled, running for the session), but when **this plugin itself is hot-reloaded** (every `main.js` rebuild during development — hot-reload disables then re-enables it) the managed plugin is *already* in that steady state, so flipping it is purely destructive: the unload makes Obsidian detach the plugin's views, and on the way back it rebuilds them through its own startup path. Measured: Glimpse's music panel was re-created as a new split at the bottom of the right sidebar (the "new tab group" semantics of `getRightLeaf(true)`), which the user saw as "a notice popped up and then the music tab moved to the lower half of the right sidebar". The predicate is now `app.plugins.enabledPlugins.has(id)`: **only "loaded + persistently enabled" is flipped** (persistently disabled already means lazy-load steady state, so it is skipped), and `flipToLazy()` carries the same guard itself (including a re-check after the queue wait), so no caller can flip a plugin that needs no conversion.
- **Verification** — after rebuilding `main.js` and letting hot-reload do its thing: `md-razor-position-cache.mirror.json` was refreshed within a second (proving this plugin really was unloaded and reloaded), while `community-plugins.json`, `workspace.json` and everything on Glimpse's side were left untouched (the old implementation rewrote the first two and reloaded Glimpse ~3s later) — i.e. reloading this plugin no longer has cross-plugin side effects.

- **The callout line-box compensation comment was rewritten for its new premise (both declarations are kept as a fallback)** — the compensation (`vertical-align: bottom` + `padding-bottom: 10px`) existed because Callout.css used `display: inline-block` to make callouts shrink to fit their content. As of 2026-09-22 the snippet uses `display: block` + `width: fit-content`: `fit-content` *is* inline-block's shrink-to-fit formula, so the adaptive width is pixel-identical (measured in the live editor: 350.88px / 86.34px for the long and short callouts, exactly as before, same 120px height), while a block-level widget is Obsidian's native geometry (the widget is its own line — no anonymous line box, no strut descent), so the height map matches the DOM by construction (all rows measured at delta = 0). **The structural fix now lives in the snippet.** The plugin keeps both declarations as a **fallback**: `vertical-align: bottom` is inert for block-level boxes but remains the key to removing the gap when the widget is still `inline-block` (older snippets or other themes), and `padding-bottom: 10px` merely preserves the previous 10px visual spacing. **No code or style behaviour changes in this release.**
- **Another trigger of the same "click/drag lands on the wrong line" family: vertical margins on line elements** — any vertical margin on a `.cm-line` (or a block widget) makes that element's border-box height differ from its flow advance, and CM6's height map sums border-box heights only (`measureVisibleLineHeights` uses `getBoundingClientRect().height`, margins excluded). Every line from there on is therefore offset by that margin, and `view.measure()` cannot repair it (re-measuring reads the same box height). The typical symptom is "press and drag right from the top half of a line and the selection lands on the previous line" — the mirror image of the "bottom half lands on the next line" bug fixed in 2.6.0. This trigger lives on the theme/snippet side (here: the Ethereal theme's consecutive-heading rule, now rewritten by the theme as "shrink the blank line between the two headings" with identical pixels), so the plugin neither can nor should fix it; the diagnostic method is recorded in DEBUGLOG for faster triage of future reports.

**2.6.4** (2026-09-16)

- **Symbol boundary hint: the `|` in the tooltip now aligns with the caret** (it no longer sits off to the right of the cursor) — previously the whole tooltip landed to the right of the caret, and the `|` inside it was separated from the caret by a distance that varied with the tooltip's content (10.6–39.2px measured), so the two appeared to move independently as the cursor moved through a marker. The cause is CM6's positioning: `writeMeasure` aligns the tooltip's **left edge** to the caret's x (`left = pos.left + offset.x`, where `offset` is the official hook CM6 provides for exactly this), while the `|` sits a further `d = border + left padding + left text width + | advance / 2` to the right. The hint now publishes `-d` through `TooltipView.offset`; `d` is measured after the tooltip is mounted (`mount()` measures the distance from the tooltip's left edge to the `|` glyph's centre), so it adapts to any font and size without maintaining a character-width formula. **Result: as the caret moves left/right inside a hidden marker, the `|` stays pinned to the caret and only the tooltip's outline grows and shrinks.** Measured in a real CM6 run: deviation was **0.00px at all 9 caret positions** (10.6–39.2px before the change).
- **The alignment offset is re-measured after zoom / font / pane-size changes** — the offset is measured at the current font size, so it goes stale when that changes. - **Fix: the symbol boundary hint was nearly invisible in dark mode** — the tooltip's fill is `--background-primary`, **exactly the same colour as the editor canvas**, so all of its depth came from `box-shadow: 0 2px 8px rgba(0,0,0,0.15)`. A black shadow's amplitude is proportional to the backdrop's brightness: the same 15% black removes about 38 code values from white (an obvious soft dark halo) but only about 4 from `#1C1C1C`, which the 8px blur then spreads into invisibility. One red herring was ruled out: **the border was not the cause** — dark `#333` against the canvas is 1.35:1, actually slightly *better* than light `#e4e4e4` against white at 1.27:1. Dark mode now gets its own override rule: the fill is derived from the canvas colour and the text colour via `color-mix` (guaranteeing it is a step lighter than the canvas), the border moves to `--background-modifier-border-focus`, and the shadow is heavier (a 1px outer dark edge plus 16px/60%). Measured across three themes: border contrast 1.31–1.35:1 → **2.29:1**, fill separation 1.19–1.21:1.
- **The dark-mode "raised surface" no longer depends on `--background-secondary`** — in dark themes that variable is usually one step lighter than the canvas (Obsidian's default ramp has base-20 > base-00, and Ethereal follows it), but that is a convention, not a contract: Blue Topaz defines it **darker** than the canvas (`#151515` vs `#202020`), which would turn the tooltip into a sunken panel there. The fill is therefore derived from the canvas itself with `color-mix(in srgb, var(--text-normal) 8%, var(--background-primary))`, keeping the "lighter" direction consistent across all three themes. The selector is `.theme-dark .mdrazor-boundary-hint.mdrazor-boundary-hint`, whose specificity `(0,3,0)` beats the original rule without `!important`, leaving light mode untouched.
- **Known limitation** — the `|` alignment is computed for LTR only; RTL paragraphs keep the previous behaviour (in RTL CM6 aligns the tooltip's right edge to the anchor, a mirrored formula under which the same negative offset would push the wrong way).

**2.5.12** (2026-09-04)

The 2.5.11 sync remeasure (for the stale-map family) and the click heal are kept.

**2.5.11** (2026-09-04)

- **Fix: dragging right from the lower half of the cursor's line selects the next line** — Same "stale height map" family as 2.5.7/2.5.9/2.5.10, in the drag scenario. - Strict triggers (as in 2.5.9): left single click only (button 0, detail ≤ 1), no modifier keys, skipping fold indicators/toggles and nested editors; **when the map is accurate (map line === DOM line) it does nothing** — zero extra measurement cost in the normal case.
